# 技术决策记录 (ADR)

## ADR-001: 独立数据表 vs 扩展现有表

**日期**: 2026-01-31
**状态**: 已接受

### 背景
需要存储会员的书签数据,有两种方案:
1. 创建独立的 `members_bookmarks` 表
2. 在 `members` 表中添加 JSON 字段存储书签列表

### 决策
选择方案 1: 创建独立的 `members_bookmarks` 表

### 理由
- **可扩展性**: 独立表支持无限数量的书签,JSON 字段有大小限制
- **查询性能**: 可以为 `member_id` 和 `created_at` 建立索引,优化查询
- **数据完整性**: 可以使用外键约束确保数据一致性
- **关系管理**: 支持级联删除,自动清理孤立数据
- **未来扩展**: 易于添加新字段(如阅读进度、笔记等)

### 后果
- 需要额外的数据库迁移
- JOIN 查询会略微增加复杂度
- 但整体架构更清晰、可维护性更强

## ADR-002: 自动注入 vs 手动集成

**日期**: 2026-01-31
**状态**: 已接受

### 背景
书签功能需要在主题中展示,有两种集成方式:
1. 通过 `{{ghost_head}}` 自动注入 JavaScript
2. 要求主题开发者手动添加 `{{bookmark_button}}` helper

### 决策
选择方案 1: 自动注入(类似 Portal/Comments UI)

### 理由
- **零配置**: 现有主题无需修改即可支持书签功能
- **用户体验**: 会员启用后立即可用,无需等待主题更新
- **一致性**: 与 Portal、Comments UI 的集成方式保持一致
- **降低门槛**: 不需要主题开发者学习新的 API

### 后果
- 需要实现智能的 DOM 查找逻辑
- 可能在某些自定义主题中位置不理想
- 但可以通过 CSS 变量和配置选项提供定制能力

## ADR-003: React Query vs Redux

**日期**: 2026-01-31
**状态**: 已接受

### 背景
前端需要状态管理方案,主要候选:
1. React Query (TanStack Query)
2. Redux + RTK Query
3. 原生 React Context + useReducer

### 决策
选择方案 1: React Query

### 理由
- **专注数据获取**: React Query 专为服务端状态管理设计
- **内置缓存**: 自动处理缓存、重新验证、后台更新
- **代码简洁**: Hook API 简单直观,减少样板代码
- **性能优化**: 自动去重请求、智能重试、乐观更新
- **生态一致**: Ghost Admin 的 React 应用已在使用 React Query

### 后果
- 增加约 15KB 的 bundle 大小
- 但显著减少手动状态管理代码
- 提供更好的用户体验(缓存、离线支持)

## ADR-004: UMD Bundle vs ES Modules

**日期**: 2026-01-31
**状态**: 已接受

### 背景
Bookmarks UI 需要在主题中加载,有两种模块格式:
1. UMD (Universal Module Definition)
2. ES Modules (ESM)

### 决策
选择方案 1: UMD Bundle

### 理由
- **浏览器兼容性**: UMD 支持所有浏览器,包括旧版本
- **全局访问**: 可以通过 `window.GhostBookmarks` 访问
- **一致性**: Portal、Comments UI 等都使用 UMD 格式
- **简单集成**: 通过 `<script>` 标签直接加载,无需构建工具

### 后果
- 无法利用现代浏览器的原生模块加载
- 但确保最大兼容性和易用性
- 可以在未来提供 ESM 版本作为可选项

## ADR-005: Members API vs Admin API

**日期**: 2026-01-31
**状态**: 已接受

### 背景
书签 API 可以放在两个位置:
1. Members API (`/members/api/bookmarks/`)
2. Admin API (`/ghost/api/admin/bookmarks/`)

### 决策
选择方案 1: Members API

### 理由
- **权限模型**: 书签是会员功能,应使用会员认证
- **安全性**: Members API 已有完善的会员会话管理
- **一致性**: 会员相关功能(订阅、评论)都在 Members API
- **访问控制**: 自动限制会员只能访问自己的书签

### 后果
- Admin 端查看会员书签需要额外的 Admin API 端点
- 但整体架构更清晰,权限边界更明确

## ADR-006: 分页 vs 无限滚动

**日期**: 2026-01-31
**状态**: 已接受

### 背景
书签列表的加载方式:
1. 传统分页(页码导航)
2. 无限滚动(滚动加载更多)
3. "加载更多"按钮

### 决策
选择方案 3: "加载更多"按钮(使用 React Query 的 `useInfiniteQuery`)

### 理由
- **用户控制**: 用户主动触发加载,不会意外加载大量数据
- **性能友好**: 避免无限滚动可能导致的内存问题
- **移动端友好**: 按钮比分页导航更适合触摸操作
- **实现简单**: React Query 的 `useInfiniteQuery` 提供完美支持

### 后果
- 需要用户主动点击加载更多
- 但提供更好的性能和用户控制感

## ADR-007: 实时同步 vs 手动刷新

**日期**: 2026-01-31
**状态**: 已接受

### 背景
多标签页/设备间的书签同步:
1. WebSocket 实时同步
2. 轮询检查更新
3. 手动刷新(依赖 React Query 缓存)

### 决策
选择方案 3: 手动刷新 + React Query 智能缓存

### 理由
- **简单性**: 无需额外的 WebSocket 基础设施
- **成本效益**: 书签不是高频操作,不需要实时同步
- **缓存策略**: React Query 的 `staleTime` 和 `refetchOnWindowFocus` 已足够
- **渐进增强**: 未来可以添加轮询或 WebSocket

### 后果
- 多标签页间不会立即同步
- 但对于书签这种低频操作,用户体验影响很小
- 可以通过窗口焦点时重新验证来改善

## 技术栈总结

| 层级 | 技术选择 | 理由 |
|------|---------|------|
| 数据库 | MySQL + 独立表 | 关系型数据,支持外键约束 |
| 后端 | Node.js + Express | Ghost 现有技术栈 |
| ORM | Bookshelf.js | Ghost 现有 ORM |
| API | Members API | 会员功能,使用会员认证 |
| 前端框架 | React 18 | 现代化,生态丰富 |
| 状态管理 | React Query | 专注服务端状态 |
| 构建工具 | Vite | 快速,支持 UMD 输出 |
| 模块格式 | UMD | 浏览器兼容性 |
| 样式方案 | CSS + 内联样式 | 简单,无依赖 |
| 测试框架 | Mocha + Playwright | Ghost 现有测试栈 |
